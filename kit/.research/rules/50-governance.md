# 50-governance · 规则单源、平台差异、自动化归属

## 1. 规则单源

- 规则只有一个**权威源**（`${rules_source}`）；各平台载体（AGENTS.md / MEMORY.md / 各客户端规则文件）都是**生成物**。
- 生成物带 GENERATED 头 + 源哈希；`--check` 失败即缺陷，先修源再重生成，**不要直接手改生成物**。
- 规则更新后，在一个合理周期内（建议 7 天）完成所有载体重生成并核对哈希。
- 直接编辑生成物的改动视为未完成。

## 2. 平台差异单独写

- 平台特有的东西（沙箱边界、技能发现根、排程能力、额度 API 归属）写进 `rules/platforms/<平台>.md`，不要污染总纲。
- 平台文件与总纲冲突时，**以总纲为准**。
- 跨平台执行同一任务时，先确认"谁写状态文件"，避免并发写坏（单一写者原则）。

## 3. 自动化归属

- 周期/定时任务**统一由一个平台承载**（建议单独指定一个，比如 cron 型客户端），其他平台不得自建。
- 同一任务禁止双跑；过渡期在每个任务的 prompt 里保留"当日去重检查"（当日已有成功结束行 → 记跳过）。
- 新增周期任务前，先登记到部署清单，再创建。

## 4. 技能与工具的权威性

- 技能只有一个权威源目录；平台副本只读同步。
- 技能 frontmatter 必须合法（`name`、`description` 必填；布尔值写 `true`/`false`，写错整个技能会被静默丢弃）。
- 工具路径集中配置（如 `tools/paths.json`），迁移平台只改一个文件。
- 消耗额度的工具（见 `metered_apis`）默认不自动调用，也不在无人值守时调用。

## 5. 自检节奏

- 每次改规则/改脚本后：跑一次 `check.mjs`（结构 + 留痕完整性）。
- 每月：扫一遍 `known_issues`（open 的要么修要么降级登记）、`runs/INDEX.md` 重建、技能副本同步核对。
- 每季度：蒸馏层新鲜度抽查（抽 3 篇看是否过期）、依赖与插件版本核对（DSH RC 线漂移会咬旧插件）。
