# 30-failure · 停、重试、归层、交接

## 1. 什么时候"停"

任一成立即断开、落盘、交还控制权：

- 用户拒绝或改变了方向
- 权限阻断（沙箱/ACL/审批失败）
- 下一步有不可逆副作用（删数据、对外发送、花钱）
- 同一动作重复空转（两次以上没有新信息）

停下时要写清：卡在哪、已确认什么、下一步需要什么（人做什么或授什么权）。**不要用"继续尝试"掩盖卡住。**

## 2. 什么时候"重试"

- 网络抖动、参数可修、无副作用 → 小步重试 **≤2 次**，保留日志。
- 同类错误**第二次出现** → 停止重试，先补规则/脚本/测试，再继续。
- 报错信息要么完整引用，要么不引用；不要转述成自己的话（会让下次 grep 不到）。

## 3. 归层（先归层再动手）

出问题先判落在哪一层，归错层会修错方向：

| 层 | 症状 | 修法 |
|---|---|---|
| 平台层 | 调度计数对不上、磁盘零痕、插件没生效 | 查载体/配置，不改业务逻辑 |
| 环境层 | 工具调不通、路径不存在、编码乱码 | 修环境，不要在业务里绕 |
| 数据层 | 源缺失、字段错、条数不足 | 补数据源或降级并标注 |
| 规范层 | 干法本身不对（框架错、判据错） | 改规则/框架 |
| 执行层 | 干到一半没了、没留痕 | 补流程与断点 |
| 观测层 | 出了问题很晚才知道 | 加指标/日志/自检 |
| 验证层 | 产出质量差但流程没报错 | 加机械校验与金标准回归 |

## 4. 会复发的问题写进"账"

- 复发问题 → 写进状态文件的 `known_issues`：现象、触发条件、修法、`last_verified`、`superseded_by`（被哪条规则/脚本取代）。
- 能用规则/脚本堵住的，当天改规则；只在对话里说"下次注意"等于没修。
- 降级运行必须登记**未验证范围 + 恢复条件**（`DEGRADED` 债务），清偿后置 `fixed`。只标不登记，等于把风险藏起来。

## 5. 中长任务三件套

预估 ≥2 个会话、或决策密度高（要拍板的事多）→ 开工第一动作建三件套：

```
tasks/<任务名>/
  AGENT.md           目标 / 边界 / 血规则（踩坑当场写，不事后补）
  CONTEXT_INDEX.md   当前步 / 下一步 / 文件地图（每步更新）
  handoff/current.md 会话交接（留最近 3 份）
```

- 已有 `AGENT.md` 视为续接：先读三件套再动手，缺件即补。
- 单会话任务不建三件套——不为齐全而写仪式。

## 6. ADR：决策备忘录（按需）

三道门槛**任一为是**才写：

1. 改主意要返工/重做
2. 未来会有人问"为什么不选另一个方案"
3. 有被放弃的选项值得留档

三条皆否 → 不建 adr 目录、不写空文件。格式只写五段：背景 / 备选项 / 选择 / 后果与代价（含放弃项的损失）/ 推翻条件（什么新证据出现时重开）。
